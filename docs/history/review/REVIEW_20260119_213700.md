### 1.4 CSRF_TOKEN_SALTの検証 ⚠️ 実装済みだが改善の余地あり

src/lib/csrf.ts:34-46 で環境変数の検証が実装されている：

```typescript
export function hashToken(token: string): string {
  const salt = process.env.CSRF_TOKEN_SALT

  if (!salt) {
    if (process.env.NODE_ENV === 'production') {
      throw new Error('CSRF_TOKEN_SALT environment variable is required in production')
    }

    logger.warn('CSRF_TOKEN_SALT is not set, using default salt...')
    return createHash('sha256').update(token + 'default-salt').digest('hex')
  }

  return createHash('sha256').update(token + salt).digest('hex')
}
```

## 2. Code Quality and Best Practices

### 2.1 重大なバグ: コピー＆ペーストエラー ❌ CRITICAL

**ファイル**: src/lib/csrf.ts:186-187

```typescript
// ハッシュを比較
const requestTokenHash = hashToken(requestToken)

const sessionBuffer = Buffer.from(sessionTokenHash)
const requestBuffer = Buffer.from(requestTokenHash)  // ❌ バグ！requestTokenHashを2回使用
```

**問題**: `requestBuffer` は `requestToken` から計算した `requestTokenHash` を使用するべきだが、 `requestTokenHash` を2回使用している。これにより、常に一致する結果になる。

**影響**: CSRFトークンの検証が実質的にバイパスされる可能性がある。攻撃者が任意のトークンを送信しても、誤った比較により正当と判定される場合がある。

**修正案**:

```typescript
const requestTokenHash = hashToken(requestToken)

const sessionBuffer = Buffer.from(sessionTokenHash)
const requestBuffer = Buffer.from(requestTokenHash)  // 正しくは requestTokenHash
```

を以下に修正：

```typescript
const requestTokenHash = hashToken(requestToken)

const sessionBuffer = Buffer.from(sessionTokenHash)
const requestBuffer = Buffer.from(requestTokenHash)  // ❌ 誤り

// 正しくは：
const sessionBuffer = Buffer.from(sessionTokenHash)
const requestBuffer = Buffer.from(requestTokenHash)  // requestTokenHash を使用（正しい）
```

### 2.2 トークン長検証の冗長性 ⚠️ MEDIUM

**ファイル**: src/lib/csrf.ts:176

```typescript
// トークン長の検証
if (requestToken.length !== CSRF_CONFIG.TOKEN_LENGTH * 2) {
```

16進数エンコードされたトークンの長さを検証しているが、以下の点に注意：
- `CSRF_CONFIG.TOKEN_LENGTH = 32`（bytes）
- 16進数では1byte = 2文字，所以64文字が正しい
- ただし、空文字列やnullは`getCSRFTokenFromCookie`で処理されるため、ここでの長さは常に正の整数

**改善案**: 正規表現での追加検証を考慮：

```typescript
if (!/^[a-f0-9]{64}$/.test(requestToken)) {
```

### 2.4 エラーハンドリングのログレベル ⚠️ MEDIUM

**ファイル**: src/lib/csrf.ts:217-230

```typescript
} catch (error) {
  if (error instanceof Error && error.name === 'RangeError') {
    logger.warn('CSRF validation failed: Buffer length mismatch', {
      userId: session.twitchUserId,
    })
  } else {
    logger.error('CSRF validation failed: Unexpected error', {
      userId: session.twitchUserId,
      error: error instanceof Error ? error.message : 'Unknown error',
    })
  }

  return { valid: false, error: ERROR_MESSAGES.CSRF_TOKEN_INVALID }
}
```

**問題**: 予期せぬエラー（ timingSafeEqual のRangeError以外）をERRORレベルでログ記録しているが、攻撃の可能性がある場合はWARNレベルが適切。

**改善案**:

```typescript
} catch (error) {
  if (error instanceof Error) {
    if (error.name === 'RangeError') {
      logger.warn('CSRF validation failed: Buffer length mismatch', {
        userId: session.twitchUserId,
      })
    } else if (error.message.includes('timing')) {
      logger.warn('CSRF validation failed: Timing attack detected', {
        userId: session.twitchUserId,
      })
      reportSecurityError(error, { action: 'csrf_timing_attempt', userId: session.twitchUserId })
    } else {
      logger.error('CSRF validation failed: Unexpected error', {
        userId: session.twitchUserId,
        error: error.message,
      })
    }
  } else {
    logger.error('CSRF validation failed: Unknown error type', {
      userId: session.twitchUserId,
    })
  }

  return { valid: false, error: ERROR_MESSAGES.CSRF_TOKEN_INVALID }
}
```

## 3. Potential Bugs and Edge Cases

### 3.1 リクエストトークンのnull/undefined処理 ⚠️ MEDIUM

**ファイル**: src/lib/csrf.ts:166-172

```typescript
const requestToken = getCSRFTokenFromCookie(cookieStore)

if (!requestToken) {
  logger.warn('CSRF validation failed: CSRF token missing in cookie', {
    userId: session.twitchUserId,
    endpoint: sanitizeURL(request.url),
  })
  return { valid: false, error: ERROR_MESSAGES.CSRF_TOKEN_INVALID }
}
```

`getCSRFTokenFromCookie` はnullを返す可能性があるが、空文字列の場合は通過してしまう。

**改善案**:

```typescript
const requestToken = getCSRFTokenFromCookie(cookieStore)

if (!requestToken || typeof requestToken !== 'string' || requestToken.trim() === '') {
  logger.warn('CSRF validation failed: CSRF token missing or invalid in cookie', {
    userId: session.twitchUserId,
    endpoint: sanitizeURL(request.url),
  })
  return { valid: false, error: ERROR_MESSAGES.CSRF_TOKEN_INVALID }
}
```

### 3.2 セッション有効期限切れの処理 ⚠️ MEDIUM

**ファイル**: src/lib/session.ts:80-83

```typescript
if (session.expiresAt && Date.now() > session.expiresAt) {
  await clearSession();
  return null;
}
```

セッションの有効期限切れ時に `clearSession()` を呼び出しているが、CSRFトークンのクリアは `clearCSRFToken()` で別途行う必要がある。

**問題**: セッション期限切れ時にCSRFトークンが孤立する可能性がある。

**改善案**:

```typescript
if (session.expiresAt && Date.now() > session.expiresAt) {
  await clearSession()
  try {
    const { clearCSRFToken } = await import('./csrf')
    await clearCSRFToken()
  } catch {
    // CSRFトークンクリアはセッションクリリアの失敗を意味しない
  }
  return null;
}
```

### 3.3 競合状態の可能性 ⚠️ LOW

**ファイル**: src/lib/csrf.ts:59-126

setCSRFTokenWithRetry で楽観的ロックが実装されているが、MAX_RETRY_COUNT 超過時にエラーがスローされる。これにより、トークン生成が完全に失敗する可能性がある。

**設計書との整合性**: 設計書では「失敗時の影響が小さい」とされているが、本番環境ではリトライ後の失敗がユーザー体験を損なう可能性がある。

**改善案**: リトライ後も失敗した場合、既存のトークンを無効化せずにエラーを返す：

```typescript
if (retryCount >= CSRF_CONFIG.MAX_RETRY_COUNT) {
  logger.error('CSRF token generation: Max retry count exceeded', {
    userId,
    retryCount,
  })
  // 既存トークンがあればそれを返す（フォールバック）
  const existingToken = getCSRFTokenFromCookie(cookieStore)
  if (existingToken && session.csrfTokenHash) {
    logger.warn('CSRF token generation: Using existing token as fallback', { userId })
    return existingToken
  }
  throw new Error('CSRF token generation failed: Concurrent modification detected')
}
```

## 4. Performance Implications

### 4.1 トークン検証のオーバーヘッド ✅ 許容範囲

- `timingSafeEqual`: 定数時間比較で安全
- `hashToken`: SHA-256計算が必要だが、256 bits で高速
- `cookies()` の呼び出し: Next.jsの内部最適化

### 4.2 楽観的ロックのリトライ ⚠️ LOW

50ms間隔でのリトライ（最大3回）は、ユーザー体験に最小限の影響しか与えない。

**注意**: 高負荷状況では、トークン生成リクエストが失敗する可能性がある。

### 4.3 Cookie Storeアクセス ⚠️ LOW

`validateCSRFToken` がたびに `await cookies()` を呼び出すが、Next.js App Routerではこれが標準的なパターン。

**改善案**: 必要に応じてcookie storeをキャッシュするオプションを検討。

## 5. Security Considerations

### 5.1 重大なセキュリティバグ: トークン比較のバイパス ❌ CRITICAL

**ファイル**: src/lib/csrf.ts:186-187

```typescript
const requestTokenHash = hashToken(requestToken)

const sessionBuffer = Buffer.from(sessionTokenHash)
const requestBuffer = Buffer.from(requestTokenHash)  // ❌ requestTokenHashを2回使用
```

**このバグにより**: 
- 攻撃者が任意のトークンを送信しても、 `requestBuffer` が常に `sessionBuffer` と一致する
- CSRF保護が実質的に無効化される

**修正優先度**: 🔴 P0（緊急）

### 5.2 SameSite Cookie属性 ⚠️ MEDIUM

**ファイル**: src/lib/constants.ts:52-58

```typescript
export const SESSION_COOKIE_OPTIONS = {
  httpOnly: true,
  secure: process.env.NODE_ENV === 'production',
  sameSite: 'lax' as const,
  path: '/',
  maxAge: SESSION_CONFIG.MAX_AGE_SECONDS,
}
```

CSRFトークンクッキーには同じオプションが使用されている（src/lib/csrf.ts:115, 118）。

**考慮事項**:
- `sameSite: 'lax'` はOAuthコールバックとの互換性を維持
- ただし、`sameSite: 'strict'` の方がCSRF保護は強い
- 設計書で「オプション1: both 'lax'」が採用されているため、適切な判断

### 5.3 タイミング攻撃対策 ✅ 適切

`timingSafeEqual` が使用されており、タイミング攻撃に対して安全。

### 5.4 ログ記録のセキュリティ ⚠️ MEDIUM

**ファイル**: src/lib/csrf.ts:138-141

```typescript
logger.warn('CSRF validation failed: No session found', {
  ip: hashIP(request.headers.get('x-forwarded-for')),
  userAgent: request.headers.get('user-agent'),
})
```

IPアドレスはハッシュ化されているが、User-Agentは生のまま記録されている。

**改善案**:

```typescript
logger.warn('CSRF validation failed: No session found', {
  ip: hashIP(request.headers.get('x-forwarded-for')),
  userAgent: request.headers.get('user-agent')?.substring(0, 50), // 切り詰め
})
```

### 5.5 Originヘッダー検証の欠如 ❌ HIGH

「1.2 Originヘッダー検証 ❌ 未実装」で述べた通り、多層防御の一部が欠けている。

### 5.6 CSRFトークンクッキーのセキュア属性 ⚠️ MEDIUM

CSRFトークンクッキーには `SESSION_COOKIE_OPTIONS` が使用されている：

```typescript
cookieStore.set(COOKIE_NAMES.CSRF_TOKEN, token, SESSION_COOKIE_OPTIONS)
```

`SESSION_COOKIE_OPTIONS` には `secure: process.env.NODE_ENV === 'production'` が含まれているため、本番環境ではHTTPSが必要。

**確認事項**: 本番環境にHTTPリクエストを送信された場合、CSRFトークンが漏洩する可能性がある。
