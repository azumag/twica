# CSRF Protection Implementation Review

**Date:** 2026-01-19
**Reviewer:** Security Code Review
**Scope:** docs/ARCHITECTURE.md, docs/IMPLEMENTED.md
**Severity:** Security-Critical Feature

---

## Executive Summary

The CSRF protection design implements a Double Submit Cookie Pattern with Hash Comparison + Token Signing. However, this review identifies **critical security flaws** that undermine the entire protection mechanism.

### Critical Finding

The design documentation (`ARCHITECTURE.md`) and implemented changes (`IMPLEMENTED.md`) are **fundamentally incompatible**:

- **ARCHITECTURE.md** specifies: non-httpOnly cookie for `csrf_token`, client reads token via `document.cookie`, sets `X-CSRF-Token` header
- **IMPLEMENTED.md** states: `CSRF_TOKEN` cookie is now `httpOnly=true`, and `validateCSRFToken()` no longer uses the `X-CSRF-Token` header

This contradiction means **the CSRF protection is either broken or not implemented as designed**. If the HttpOnly pattern is implemented as documented in IMPLEMENTED.md, the client cannot read the token to set the required header, making CSRF protection impossible.

**Overall Assessment: NOT READY FOR PRODUCTION** - Critical design contradictions and security vulnerabilities must be resolved.

## Critical Issues (Must Fix Before Production)

### C1. Design Contradiction Between Documentation and Implementation

**Location:** ARCHITECTURE.md:00273-00279 vs IMPLEMENTED.md:00008-00009

**Problem:** The two documents describe incompatible implementations.

ARCHITECTURE.md specifies non-httpOnly cookie:
```typescript
// ARCHITECTURE.md:273
cookieStore.set('csrf_token', token, {
  httpOnly: false, // MUST be false for JS access
  // ...
})
```

IMPLEMENTED.md claims httpOnly was implemented:
```typescript
// IMPLEMENTED.md:8
CSRF_TOKEN cookie to httpOnly=true
```

**Impact:** 
- If httpOnly=true is implemented: Client cannot read token, cannot set `X-CSRF-Token` header, CSRF protection fails
- If non-httpOnly is kept: XSS attacker can read token, defeating CSRF protection
- Neither document accurately reflects the current state

**Recommendation:**
1. Clarify which approach is actually implemented
2. If HttpOnly is required, redesign to use cookie-to-cookie comparison (synchronizer token pattern)
3. Update both documents to be consistent
4. Add architectural diagram showing actual data flow

### C2. Hardcoded Fallback Signing Key

**Location:** ARCHITECTURE.md:01042

```typescript
const SIGNING_KEY = process.env.CSRF_SIGNING_KEY || 'default-key-change-in-production'
```

**Problem:** 
- Hardcoded fallback key for development/testing
- If `CSRF_SIGNING_KEY` environment variable is not set (misconfiguration), the system uses a known weak key
- Attackers can exploit misconfigured deployments to forge CSRF tokens

**CVSS Score:** 9.8 (Critical) - Remote code execution equivalent in CSRF context

**Recommendation:**
```typescript
// NEVER fallback to default key
const SIGNING_KEY = process.env.CSRF_SIGNING_KEY
if (!SIGNING_KEY) {
  throw new Error('CSRF_SIGNING_KEY environment variable is required')
}
```

### C3. No Origin/Referer Header Validation

**Location:** ARCHITECTURE.md:00296-00364 (validateCSRFToken)

**Problem:** The validation function only checks the CSRF token but does not validate:
- `Origin` header
- `Referer` header

These headers provide defense-in-depth against CSRF attacks.

**Recommendation:** Add Origin/Referer validation:
```typescript
export async function validateCSRFToken(
  request: Request
): Promise<{ valid: boolean; error?: string }> {
  // Existing token validation...
  
  // Add: Origin/Referer validation for state-changing requests
  const origin = request.headers.get('origin')
  const referer = request.headers.get('referer')
  const validOrigins = process.env.ALLOWED_ORIGINS?.split(',') || []
  
  if (origin && !validOrigins.includes(origin)) {
    logger.warn('CSRF validation failed: Invalid origin', {
      origin,
      userId: session.twitchUserId,
    })
    return { valid: false, error: ERROR_MESSAGES.CSRF_TOKEN_INVALID }
  }
  
  // Continue with token validation...
}
```

### C4. Token Entropy Insufficient for 256-bit Claim

**Location:** ARCHITECTURE.md:00213

```typescript
const CSRF_TOKEN_LENGTH = 32 // 256 bits
```

**Problem:** The comment claims 256 bits of entropy, but:
- `crypto.randomBytes(32)` generates 32 bytes (256 bits) of randomness
- However, the hex encoding (line 221) expands this to 64 characters, not increasing entropy
- No explicit entropy source verification

**Recommendation:** 
- Verify `crypto.randomBytes` uses cryptographically secure random number generator (CSPRNG)
- Consider using base64url encoding to maintain entropy in shorter string representation
- Document the entropy source and strength

## Major Issues (Must Fix Before Release)

### M1. Race Condition in Token Generation

**Location:** ARCHITECTURE.md:00234-00290 (setCSRFToken function)

```typescript
// Idempotent check - but not atomic
if (session.csrfTokenHash) {
  const existingToken = getCSRFTokenFromCookie(cookieStore)
  if (existingToken) {
    return existingToken
  }
}
// Generate new token...
```

**Problem:**
1. Check-then-act race condition between reading session and updating it
2. Multiple concurrent requests could all pass the `if (!session.csrfTokenHash)` check
3. Last writer wins, potentially causing legitimate tokens to be invalidated
4. The idempotent design document acknowledges this but calls it "low frequency" - not acceptable for security-critical code

**Attack Scenario:**
1. User has valid session with CSRF token T1
2. Two tabs open simultaneously, both call setCSRFToken()
3. Both read session, see csrfTokenHash exists
4. Both read cookie, get T1
5. First request completes, nothing changes
6. User performs action with T1
7. Second request (after first) generates T2
8. T1 is now invalid, user action fails

**Recommendation:** Implement proper synchronization:
```typescript
export async function setCSRFToken(): Promise<string> {
  const cookieStore = await cookies()
  
  // Use optimistic locking with version check
  for (let attempt = 0; attempt < CSRF_CONFIG.MAX_RETRY_COUNT; attempt++) {
    const sessionCookie = cookieStore.get(COOKIE_NAMES.SESSION)?.value
    if (!sessionCookie) {
      throw new Error('No session found')
    }
    
    const session = parseSession(sessionCookie)
    const existingToken = getCSRFTokenFromCookie(cookieStore)
    
    // If token exists and matches session hash, return it
    if (existingToken && session.csrfTokenHash) {
      if (verifyTokenHash(existingToken, session.csrfTokenHash)) {
        return existingToken
      }
    }
    
    // Generate new token with atomic session update
    const newToken = generateCSRFToken()
    const newHash = hashToken(newToken)
    
    const updatedSession = {
      ...session,
      csrfTokenHash: newHash,
      version: (session.version || 0) + 1,
    }
    
    // Attempt atomic update - if version mismatch, retry
    const success = await atomicSessionUpdate(updatedSession, session.version)
    if (success) {
      // Set cookie only on success
      cookieStore.set('csrf_token', newToken, { /* options */ })
      return newToken
    }
    
    // Retry on version mismatch
    await new Promise(resolve => setTimeout(resolve, CSRF_CONFIG.RETRY_DELAY_MS))
  }
  
  throw new Error('Failed to generate CSRF token after retries')
}
```

### M3. Inconsistent Error Logging with User IP Disclosure Risk

**Location:** ARCHITECTURE.md:00303-00306, 00340-00345

**Problem:** 
1. IP addresses logged in plain text
2. User-Agent logged without sanitization
3. `request.headers.get('x-forwarded-for')` could contain multiple IPs

**Current (problematic):**
```typescript
logger.warn('CSRF validation failed: No session found', {
```

**Recommendation:**
```typescript
logger.warn('CSRF validation failed: No session found', {
  // Hash IP with salt, keep only first 8 characters for uniqueness
  ipHash: hashIp(request.headers.get('x-forwarded-for') || ''),
  // Sanitize user agent
  userAgent: sanitizeUserAgent(request.headers.get('user-agent')),
})
```

### M4. Cookie Settings Inconsistency

**Location:** ARCHITECTURE.md:00264-00279

**Problem:** Different cookie settings between session and CSRF token:

```typescript
// Session cookie (line 264-270)
cookieStore.set(COOKIE_NAMES.SESSION, JSON.stringify(updatedSession), {
  httpOnly: true,
  secure: process.env.NODE_ENV === 'production',
  sameSite: 'lax',
  path: '/',
  maxAge: SESSION_CONFIG.MAX_AGE_SECONDS,
})

// CSRF token cookie (line 273-279)
cookieStore.set('csrf_token', token, {
  httpOnly: false, // Contradicts IMPLEMENTED.md
  secure: process.env.NODE_ENV === 'production',
  sameSite: 'lax',
  path: '/',
  maxAge: SESSION_CONFIG.MAX_AGE_SECONDS,
})
```

**Problem:** 
- `maxAge` is not set for session cookie (relies on browser session)
- `expires` not set for either cookie
- Inconsistent security posture

**Recommendation:** Use consistent, secure settings:
```typescript
const COOKIE_OPTIONS = {
  httpOnly: true,  // Or false based on design decision
  secure: true,    // Always true in production
  sameSite: 'lax',
  path: '/',
  maxAge: SESSION_CONFIG.MAX_AGE_SECONDS,
  expires: new Date(Date.now() + SESSION_CONFIG.MAX_AGE_SECONDS * 1000),
}
```

## Medium Issues (Should Fix Before Release)

### MED1. Missing Token Rotation on Privileged Actions

**Location:** ARCHITECTURE.md (general design)

**Problem:** Tokens are not rotated after sensitive actions:
- Password change
- Email change
- Account deletion
- Payment operations

**Recommendation:** Implement token rotation on sensitive actions:
```typescript
export async function rotateCSRFTokenAfterSensitiveAction(): Promise<string> {
  // Invalidate current token
  await clearCSRFToken()
  // Generate new token
  return await setCSRFToken()
}
```

### MED5. Missing Security Headers in API Responses

**Location:** ARCHITECTURE.md (general)

**Problem:** API responses don't include security headers:
- `X-Content-Type-Options: nosniff`
- `X-Frame-Options: DENY`
- `Cache-Control: no-store, no-cache, must-revalidate`

**Recommendation:** Add middleware for security headers:
```typescript
export function withSecurityHeaders(response: NextResponse): NextResponse {
  response.headers.set('X-Content-Type-Options', 'nosniff')
  response.headers.set('X-Frame-Options', 'DENY')
  response.headers.set('Cache-Control', 'no-store, no-cache, must-revalidate')
  return response
}
```

### MIN2. Missing Deprecation Plan for Old Sessions

**Location:** ARCHITECTURE.md (general)

**Problem:** No migration plan for existing sessions without CSRF tokens:
- Users with existing sessions won't have `csrfTokenHash`
- First request after deployment will fail validation

**Recommendation:** Implement graceful migration:
```typescript
export async function validateCSRFToken(request: Request) {
  const session = await getSession()
  
  // Graceful migration: allow requests without CSRF for existing sessions
  if (!session.csrfTokenHash) {
    logger.info('CSRF migration: Session without token', {
      userId: session.twitchUserId,
    })
    // Generate token and continue (one-time migration)
    await setCSRFToken()
    return { valid: true, migrated: true }
  }
  // ... continue with validation
}
```

## Conclusion

The CSRF protection design shows good understanding of security concepts (Double Submit Cookie Pattern, timing-safe comparison, token signing). However, **critical implementation issues** prevent this from being production-ready:

1. **Fundamental design contradiction** between documentation and implementation
2. **Hardcoded cryptographic key** undermines entire signing mechanism
3. **Missing defense-in-depth** (Origin validation)

**Status: NOT APPROVED FOR PRODUCTION**

The issues marked P0 must be resolved before any deployment. A follow-up review is required after fixes are implemented.
