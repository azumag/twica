## New Issues Discovered

### 1. Missing Session Expiration Check in Validation (Security Risk)

**Location:** `src/lib/csrf.ts:124-256`

**Issue:**
While `setCSRFToken` checks session expiration (line 78-81), `validateCSRFToken` does not validate session expiration. This means an expired session could still pass CSRF validation.

**Current Code:**
```typescript
export async function validateCSRFToken(
  request: Request
): Promise<{ valid: boolean; error?: string }> {
  const cookieStore = await cookies()
  const sessionCookie = cookieStore.get(COOKIE_NAMES.SESSION)?.value

  if (!sessionCookie) {
    // ... no session handling
  }

  const session = parseSession(sessionCookie)
  const sessionTokenHash = session.csrfTokenHash

  // No expiration check here!
```

**Problem:**
An expired session with a valid CSRF token could still pass validation, which defeats the purpose of session expiration.

**Recommended Fix:**
```typescript
const session = parseSession(sessionCookie)

// Check session expiration
if (session.expiresAt && Date.now() > session.expiresAt) {
  logger.warn('CSRF validation failed: Session expired', {
    userId: session.twitchUserId,
  })
  return { valid: false, error: ERROR_MESSAGES.CSRF_TOKEN_INVALID }
}

const sessionTokenHash = session.csrfTokenHash
```

**Severity:** High - Security vulnerability

### 2. Unnecessary Version Increment in clearCSRFToken (Code Quality)

**Location:** `src/lib/csrf.ts:261-283`

**Issue:**
The `clearCSRFToken` function increments the session version when clearing the CSRF token. This is inconsistent with the design where version increments are only needed during concurrent modification scenarios (token generation).

**Current Code:**
```typescript
export async function clearCSRFToken(): Promise<void> {
  const cookieStore = await cookies()
  const sessionCookie = cookieStore.get(COOKIE_NAMES.SESSION)?.value

  if (!sessionCookie) {
    return
  }

  const session = parseSession(sessionCookie)

  // セッションからハッシュを削除し、バージョン番号をインクリメント
  if (session.csrfTokenHash) {
    const sessionWithoutCsrf = { ...session, version: session.version + 1 }
    delete sessionWithoutCsrf.csrfTokenHash

    cookieStore.set(COOKIE_NAMES.SESSION, JSON.stringify(sessionWithoutCsrf), SESSION_COOKIE_OPTIONS)
  }

  // ...
}
```

**Problem:**
- No race condition exists when clearing a token (typically happens during logout)
- Version increment adds unnecessary complexity
- Inconsistent with the rest of the design

**Recommended Fix:**
```typescript
// セッションからハッシュを削除
if (session.csrfTokenHash) {
  const sessionWithoutCsrf = { ...session }
  delete sessionWithoutCsrf.csrfTokenHash

  cookieStore.set(COOKIE_NAMES.SESSION, JSON.stringify(sessionWithoutCsrf), SESSION_COOKIE_OPTIONS)
}
```

**Severity:** Low - Code quality issue

### 3. Exposed retryCount Parameter (Code Quality)

**Location:** `src/lib/csrf.ts:48`

**Issue:**
The `setCSRFToken` function exposes `retryCount` as a public parameter, which is an implementation detail for optimistic locking retry logic.

**Current Code:**
```typescript
export async function setCSRFToken(retryCount: number = 0): Promise<string> {
```

**Problem:**
- Exposes internal retry logic to external callers
- Callers could incorrectly manipulate the retry behavior
- Breaks encapsulation

**Recommended Fix:**
Make retryCount a private parameter by creating an internal function:

```typescript
async function setCSRFTokenWithRetry(retryCount: number = 0): Promise<string> {
  // Existing implementation
}

export async function setCSRFToken(): Promise<string> {
  return setCSRFTokenWithRetry(0)
}
```

Or use a default export pattern.

**Severity:** Low - Code quality/capsulation issue
