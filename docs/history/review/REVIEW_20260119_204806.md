## 2. Potential Bugs & Edge Cases

### Issues

#### BUG-01: **Default Salt Value is Security Vulnerability**
- **Location:** `docs/IMPLEMENTED.md` line 29
- **Issue:** Salt implementation uses default value: `process.env.CSRF_TOKEN_SALT || 'default-salt'`
- **Security Risk:**
  - If `CSRF_TOKEN_SALT` is not configured, all deployments use `'default-salt'`
  - Attackers can pre-compute rainbow tables for `'default-salt'`
  - Same salt across multiple deployments allows cross-site rainbow table attacks
- **Example Attack:**
  ```typescript
  // Attack scenario:
  // Attacker knows salt is 'default-salt'
  // They can pre-compute hash("random-token-1234" + "default-salt")
  // If they obtain a session's csrfTokenHash, they can reverse-engineer valid tokens
  ```
- **Severity:** **CRITICAL** - Security vulnerability
- **Recommendation:**
  1. Remove default salt value
  2. Fail fast if `CSRF_TOKEN_SALT` is not configured:
     ```typescript
     const salt = process.env.CSRF_TOKEN_SALT
     if (!salt) {
       throw new Error('CSRF_TOKEN_SALT environment variable is required')
     }
     ```
  3. Generate random salt at application startup if preconfigured salt is not acceptable
  4. Document salt generation and rotation process

#### BUG-02: **Salt Not Included in Session Version Check**
- **Location:** `docs/IMPLEMENTED.md` (not explicitly shown, inferred)
- **Issue:** If salt changes, all existing CSRF tokens become invalid without a session version bump.
- **Impact:** Users will experience authentication failures after salt rotation.
- **Severity:** **MEDIUM** - UX issue
- **Recommendation:** Consider including salt version in session data to detect salt changes.

#### BUG-03: **Race Condition in setCSRFToken Not Fully Addressed**
- **Location:** `docs/ARCHITECTURE.md` lines 234-252 (setCSRFToken)
- **Issue:** The architecture document shows idempotent check:
  ```typescript
  if (session.csrfTokenHash) {
    const existingToken = getCSRFTokenFromCookie(cookieStore)
    if (existingToken) {
      return existingToken
    }
  }
  ```
- **TOCTOU Vulnerability:** Race condition exists between `session.csrfTokenHash` check and `getCSRFTokenFromCookie` call.
- **Verification:** Need to verify actual implementation in `src/lib/csrf.ts` has the fix:
  ```typescript
  const existingToken = getCSRFTokenFromCookie(cookieStore)
  if (session.csrfTokenHash && existingToken) {
    return existingToken
  }
  ```
- **Severity:** **HIGH** - Potential race condition
- **Recommendation:** Update `ARCHITECTURE.md` to show the correct implementation pattern.

### Critical Issues

#### SEC-01: **DEFAULT SALT VALUE IS CRITICAL SECURITY FLAW** ⚠️
- **Location:** `docs/IMPLEMENTED.md` line 29
- **Issue:** Using `'default-salt'` as fallback completely undermines the security benefit of salting.
- **Why This is Critical:**
  - **Purpose of salt:** Prevent rainbow table attacks by ensuring each deployment uses unique salt
  - **With default salt:** All deployments using default salt are vulnerable to rainbow table attacks
  - **Attack vector:**
    1. Attacker obtains a session's `csrfTokenHash`
    2. Attacker knows or guesses default salt is used
    3. Attacker generates rainbow table for `'default-salt'`
    4. Attacker finds token that matches `csrfTokenHash`
    5. Attacker can now forge CSRF tokens for that session
- **Example Attack Code:**
  ```javascript
  // Attacker generates rainbow table
  const salt = 'default-salt'
  const rainbowTable = {}
  
  for (let i = 0; i < 1000000; i++) {
    const token = generateRandomToken()
    const hash = sha256(token + salt)
    rainbowTable[hash] = token
  }
  
  // Attacker obtains session.csrfTokenHash from compromised session
  const stolenHash = getSessionHash()
  
  // Attacker finds matching token in rainbow table
  const forgedToken = rainbowTable[stolenHash]
  
  // Attacker can now forge CSRF requests
  await fetch('/api/delete-user', {
    method: 'POST',
    headers: { 'X-CSRF-Token': forgedToken }
  })
  ```
- **Severity:** **CRITICAL** - Complete bypass of CSRF protection if salt is default
- **Recommendation:** IMMEDIATE ACTION REQUIRED
  1. Remove default salt value
  2. Make salt configuration mandatory with application startup validation
  3. Generate strong random salt at deployment time if preconfigured salt is not used
  4. Document salt generation, rotation, and security procedures

## 5. Code Simplicity

### Issues

#### SIMP-01: **Over-Engineered Optimistic Locking Still Present**
- **Location:** `docs/ARCHITECTURE.md` lines 181-189, `docs/IMPLEMENTED.md` (setCSRFTokenWithRetry)
- **Issue:** Architecture specifies version-based optimistic locking with retry logic (max 3 retries, 10ms delay).
- **Analysis:**
  - CSRF token generation happens once per session
  - Race condition risk is theoretical, not practical
  - Retry logic adds complexity for negligible benefit
- **Code Complexity:**
  ```typescript
  // Complex retry logic for low-risk scenario
  async function setCSRFTokenWithRetry(session: Session, maxRetries: number = 3): Promise<string> {
    for (let i = 0; i < maxRetries; i++) {
      try {
        return await setCSRFToken(session)
      } catch (error) {
        if (i === maxRetries - 1) throw error
        await sleep(10)
      }
    }
    throw new Error('Max retries exceeded')
  }
  ```
- **Alternative:** Simplify to basic version check without retries:
  ```typescript
  if (session.version !== currentSession.version) {
    throw new Error('Session version mismatch')
  }
  ```
- **Severity:** **LOW** - Code complexity issue
- **Recommendation:** Remove retry logic; keep version check only for collision detection.

#### SIMP-02: **Complex Error Handling Persists**
- **Location:** `docs/ARCHITECTURE.md` lines 296-363 (validateCSRFToken)
- **Issue:** Function has complex error handling with multiple try-catch blocks and different log levels.
