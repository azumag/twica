# CSRF保護実装レビュー

レビュー日時: 2026-01-19 21:01:49
レビュー対象: docs/ARCHITECTURE.md (Issue #55: Critical Security - Missing CSRF Protection) と実装コード

## 重大な問題

### 1. Origin/Refererヘッダー検証の実装漏れ

**場所**: `src/lib/csrf.ts`

**問題**:
設計書（ARCHITECTURE.md:362-399）ではOrigin/Refererヘッダーの検証が明記されていますが、実際の実装には含まれていません。

設計書の仕様:
```typescript
// Originヘッダーの検証（多層防御として）
const origin = request.headers.get('origin')
const referer = request.headers.get('referer')
const requestUrl = new URL(request.url)
const expectedOrigin = `${requestUrl.protocol}//${requestUrl.host}`

if (origin && !CSRF_CONFIG.ALLOWED_ORIGINS.includes(origin)) {
  logger.warn('CSRF validation failed: Origin header not in allowed list', {...})
  return { valid: false, error: ERROR_MESSAGES.CSRF_TOKEN_INVALID }
}

// Originヘッダーがない場合、Refererヘッダーを検証（オプション）
if (!origin && referer) {
  // Referer検証ロジック
}
```

実装状況:
- `validateCSRFToken` 関数（src/lib/csrf.ts:121-221）にOrigin/Referer検証が含まれていない
- 多層防御の第3層が欠如

**影響**: 脆弱性の強度が低下、SameSite='lax'とCSRFトークンの2層のみで防御

---

### 2. テストコードと設計の不一致

**場所**:
- `tests/unit/csrf.test.ts`
- `tests/integration/csrf.test.ts`

**問題**:
設計ではHttpOnly Cookie Patternを採用し、X-CSRF-Tokenヘッダーは不要と記述されていますが、テストコードは依然としてX-CSRF-Tokenヘッダーの検証をテストしています。

不一致箇所:
- tests/unit/csrf.test.ts:167-206 - `validateCSRFToken`がX-CSRF-Tokenヘッダーからトークンを取得することを想定
- tests/integration/csrf.test.ts:243-266 - Double Submit Cookie Patternに関するテストが残っている

設計書の記述（ARCHITECTURE.md:487-494）:
```
**HttpOnly Cookie Patternでは不要**

HttpOnly Cookie Patternでは、トークンがhttpOnly cookieに保存されるため、クライアントにトークンを返すAPIは不要です。
- トークンはcookie経由で自動的に送信されます
- JavaScriptからトークンにアクセスする必要がありません
- APIエンドポイントは削除します
```

**影響**: テストが実装と一致しておらず、意図した動作を検証できていない可能性

---

### 3. APIルートへのCSRF保護の一貫性欠如

**問題**:
一部の状態変更APIルートにCSRF保護が適用されていない可能性があります。

確認済み（CSRF保護あり）:
- `/api/battle/start` (POST) ✓
- `/api/cards` (POST) ✓
- `/api/cards/[id]` (PUT, DELETE) ✓
- `/api/gacha` (POST) ✓
- `/api/upload` (POST) ✓
- `/api/streamer/settings` (POST) ✓
- `/api/twitch/rewards` (POST) ✓
- `/api/twitch/eventsub/subscribe` (POST) ✓
- `/api/gacha-history/[id]` (DELETE) ✓
- `/api/auth/logout` (POST) ✓

未確認・疑問点:
- EventSub webhook (`/api/twitch/eventsub`) はTwitchからの署名検証のみで、CSRF保護は不要（正しい判断）
- その他のDELETE/PUT/PATCHエンドポイントを網羅的に確認が必要

**影響**: 状態変更操作の一部でCSRF保護が適用されていない可能性がある

---

### 4. /api/auth/logoutのGETメソッドでのCSRF保護欠如

**場所**: `src/app/api/auth/logout/route.ts`

**問題**:
GETリクエストでログアウトが可能になっており、CSRF保護が適用されていません。

```typescript
// POSTメソッド - CSRF保護あり
export async function POST(request: Request) {
  // ... CSRF検証あり
  const csrfValidation = await validateCSRFToken(request);
  if (!csrfValidation.valid) {
    return NextResponse.redirect(`${process.env.NEXT_PUBLIC_APP_URL}/?error=${encodeURIComponent(ERROR_MESSAGES.FORBIDDEN)}`);
  }
  // ...
}

// GETメソッド - CSRF保護なし
export async function GET(request: Request) {
  // ... CSRF検証なし
  // セッションとCSRFトークンを削除してリダイレクト
}
```

**影響**: 攻撃者が `<img>` タグやリンクを使用して、ユーザーのセッションを終了させるCSRF攻撃が可能

---

### 5. 設計書と実装のエラーハンドリングの不一致

**場所**: `src/lib/csrf.ts`

**問題**:
設計書ではエラーの種類に応じて異なるログレベルを使用すると記述されていますが、実装では簡略化されています。

設計書（ARCHITECTURE.md:1039-1071）:
```typescript
// 設計: タイミング攻撃の疑いがある場合（WARN）
logger.warn('CSRF token validation failed: Token mismatch (potential attack)', {...})
// 設計: バッファ長不一致（INFO）
logger.warn('CSRF validation failed: Buffer length mismatch', {...})
```

実装（src/lib/csrf.ts:208-220）:
```typescript
// 実装: すべて同じエラーメッセージで403を返す
catch (error) {
  if (error instanceof Error && error.name === 'RangeError') {
    logger.warn('CSRF validation failed: Buffer length mismatch', {...})
  } else {
    logger.error('CSRF validation failed: Unexpected error', {...})
  }
  return { valid: false, error: ERROR_MESSAGES.CSRF_TOKEN_INVALID }
}
```

**影響**: セキュリティイベントの重要度が適切に区別されていない

## 重大度の低い問題

### 6. 定数定義の不完全さ

**場所**: `src/lib/constants.ts:62`

**問題**:
`CSRF_CONFIG.HEADER_NAME` が定義されていますが、HttpOnly Cookie Patternでは使用されていません。

```typescript
export const CSRF_CONFIG = {
  TOKEN_LENGTH: 32,
  HEADER_NAME: 'X-CSRF-Token', // ← 使用されていない
  MAX_RETRY_COUNT: 3,
  RETRY_DELAY_MS: 50,
  ALLOWED_ORIGINS: [...],
}
```

**影響**: コードの可読性が下がる、不要な定義が残っている

---

### 7. ミドルウェアの未使用

**場所**: `src/lib/middleware/csrf.ts`

**問題**:
CSRF保護ミドルウェアが定義されていますが、実際のAPIルートでは直接 `validateCSRFToken` を呼び出しており、ミドルウェアは使用されていません。

**影響**: ミドルウェアパターンの利点（一貫性、DRY）が活用されていない

## 実装状況の評価

### ✅ 実装済み

1. **CSRFトークン生成** (`src/lib/csrf.ts`)
   - 32バイト（256ビット）の暗号学的に安全な乱数
   - 楽観的ロックによる競合状態対策

2. **HttpOnly Cookie Pattern**
   - トークンをhttpOnly cookieに保存
   - JavaScriptからのアクセス不可

3. **セッションへのトークンハッシュ保存**
   - SHA-256によるハッシュ化
   - タイミング攻撃に対して安全な比較（timingSafeEqual）

4. **ログアウト時のトークン削除**
   - セッションからトークンハッシュを削除
   - httpOnly cookieも削除

5. **楽観的ロック**
   - セッションにバージョン番号を追加
   - トークン生成時にバージョン検証

6. **セキュリティ配慮のあるログ**
   - IPアドレスのSHA-256ハッシュ化
   - URLのサニタイズ

### ❌ 未実装

1. **Origin/Refererヘッダー検証**
   - 多層防御の第3層

2. **テストコードの更新**
   - HttpOnly Cookie Patternに対応したテスト

## コード品質

### 良い点

1. **型安全性**: TypeScriptで適切に型定義されている
2. **エラーハンドリング**: try-catchで適切にエラーを処理
3. **ログ記録**: 詳細なログでデバッグ性が高い
4. **セキュリティ**: timingSafeEqual、SHA-256ハッシュ化など適切なセキュリティ対策

### 改善点

1. **一貫性**: CSRF保護の適用方法が統一されていない
2. **簡潔さ**: ミドルウェアが定義されているが使用されていない
3. **テストカバレッジ**: HttpOnly Cookie Patternに対応したテストが必要

---

## パフォーマンス

- トークン検証にハッシュ計算が必要だが、SHA-256は高速なので問題ない
- 楽観的ロックのリトライ回数（最大3回）は適切
- 同一リクエスト内で複数回cookieを取得している（パフォーマンスへの影響は最小限）

---

## セキュリティ

### 強い点

1. **HttpOnly Cookie**: XSS攻撃時にトークンが窃取されない
2. **SameSite='lax'**: クロスサイトPOSTリクエストを防止
3. **タイミング攻撃対策**: timingSafeEqualを使用
4. **十分なエントロピー**: 256ビットのトークン

### 弱い点

1. **Origin/Referer検証の欠如**: 多層防御が不完全
2. **GETリクエストでのログアウト**: CSRF攻撃のリスク

---

## 推奨される修正アクション

### 優先度1（重大）

1. **Origin/Refererヘッダー検証を追加する**
   - `validateCSRFToken` 関数に検証ロジックを追加
   - ARCHITECTURE.md:362-399 の仕様を実装

2. **/api/auth/logoutのGETメソッドを削除またはCSRF保護を追加する**
   - GETメソッドでのログアウトを禁止するか、CSRF保護を適用する必要がある
   - 推奨: GETメソッドを削除し、POSTのみにする

3. **テストコードをHttpOnly Cookie Patternに更新する**
   - X-CSRF-Tokenヘッダーに関するテストを削除
   - Cookieからのトークン取得をテストする

### 優先度2（重要）

4. **全APIルートのCSRF保護状況を確認する**
   - 全POST/PUT/DELETE/PATCHエンドポイントを網羅的に確認
   - 保護が適用されていないルートに `validateCSRFToken` を追加

5. **ミドルウェアを使用するか削除する**
   - `src/lib/middleware/csrf.ts` を使用するか、削除してコードベースを整理

### 優先度3（改善）

6. **未使用の定数を削除する**
   - `CSRF_CONFIG.HEADER_NAME` を削除

---

## 結論

### 全体的評価: ⚠️ 実装が必要だが、設計と実装に不一致あり

CSRF保護の基本的な実装は適切に行われていますが、以下の重大な問題があります：

1. **Origin/Refererヘッダー検証が実装されていない** - 設計で指定された多層防御の一部が欠如
2. **テストコードが設計と一致していない** - HttpOnly Cookie Patternに対応したテストが必要
3. **GETリクエストでのログアウトがCSRF保護なし** - 重大なセキュリティリスク

### 修正が必要

以下の問題を修正するまで、実装は不完全と判断します：

1. Origin/Refererヘッダー検証の実装
2. GETメソッドでのログアウトのCSRF保護
3. テストコードの更新
