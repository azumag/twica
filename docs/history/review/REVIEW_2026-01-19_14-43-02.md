## 3. 各問題点の詳細と修正方法

### 🔴 H-1: SameSite='lax'の解釈に関する誤解

**詳細**:
設計書（docs/ARCHITECTURE.md:18）で `sameSite: 'lax'` が「⚠️ CSRF脆弱性」として記載されていますが、これは正確な説明ではありません。

SameSite='lax'は実際には**セキュリティ機能**であり、以下の保護を提供します：
- クロスサイトPOSTリクエストではCookieが送信されない
- トップレベルナビゲーションでのGETリクエストのみ許可

SameSite='lax'とCSRFトークンの組み合わせは、**防御の深層化（Defense in Depth）**として機能します。設計書の表現は、SameSite='lax'単独では完全なCSRF保護を提供しないという正しい認識を反映していますが、「脆弱性」という表現は誤解を招きます。

**修正方法**:
```markdown
# 修正前（ARCHITECTURE.md:18）
sameSite: 'lax',  // ⚠️ CSRF脆弱性

# 修正後
sameSite: 'lax',  // CSRFトークンとの併用で多層防御を実現
```

また、設計書の「攻撃シナリオ」セクション（docs/ARCHITECTURE.md:44-65）を更新し、SameSite='lax'の保護機能を正確に説明してください。

### 🔴 H-2: localStorage使用によるXSS脆弱性

**詳細**:
実装（src/lib/client/csrf.ts:406-410）でCSRFトークンをlocalStorageに保存しています：

```typescript
if (!csrfToken) {
  csrfToken = await fetchCSRFToken()
  localStorage.setItem('csrfToken', csrfToken)  // XSS攻撃で窃取可能
}
```

localStorageはJavaScriptからアクセス可能であるため、XSS脆弱性が存在する場合、攻撃者がCSRFトークンを窃取し、任意のアクションを実行できます。

**修正方法**:

以下の2つのアプローチがあります：

**アプローチA: httpOnly Cookieに移行（推奨）**

```typescript
// src/lib/client/csrf.ts を修正
export async function fetchWithCSRF(
  url: string,
  options: RequestInit = {}
): Promise<Response> {
  const method = (options.method || 'GET').toUpperCase()

  if (['POST', 'PUT', 'DELETE'].includes(method)) {
    // Cookieからトークンを取得（httpOnly、JSからはアクセス不可）
    const token = await getCSRFTokenFromCookie()
    
    options.headers = {
      ...options.headers,
      'X-CSRF-Token': token,
    }
  }

  return fetch(url, options)
}

async function getCSRFTokenFromCookie(): Promise<string> {
  // Cookieから直接読み取り（JSからはアクセス不可）
  const cookies = document.cookie.split('; ')
  const csrfCookie = cookies.find(c => c.startsWith('csrf_token='))
  return csrfCookie ? csrfCookie.split('=')[1] : ''
}
```

さらに、サーバー側でCookieも設定します：

```typescript
// src/lib/csrf.ts の setCSRFToken() を修正
export async function setCSRFToken(): Promise<string> {
  // ... 既存のロジック ...

  // httpOnly Cookieにも保存
  cookieStore.set('csrf_token', token, {
    httpOnly: true,  // JavaScriptからアクセス不可
    secure: process.env.NODE_ENV === 'production',
    sameSite: 'strict',  // 厳格モード
    path: '/',
    maxAge: 7 * 24 * 60 * 60,
  })

  return token
}
```

**アプローチB: セッションCookieに埋め込む（既存設計の改良）**

現在の設計ではCSRFトークンはセッションCookie内にJSONで保存されています。この場合：
- セッションCookieはhttpOnly=Trueであるため、JSからはアクセス不可
- ただし、`fetchCSRFToken()` APIでトークンをクライアントに返す必要がある

実装を以下のように変更：

```typescript
// src/app/api/csrf-token/route.ts
// トークンをAPIレスポンスのSet-Cookieヘッダーでも返す

export async function GET() {
  // ... 既存のロジック ...
  
  const response = NextResponse.json({ csrfToken: token })
  
  // httpOnly Cookieでトークンを返す
  response.cookies.set('csrf_token', token, {
    httpOnly: true,
    secure: process.env.NODE_ENV === 'production',
    sameSite: 'strict',
    path: '/',
    maxAge: 7 * 24 * 60 * 60,
  })
  
  return response
}
```

クライアント側ではCookieからトークンを読み取るように変更します。

### 🔴 H-3: トークン長検証のタイミング攻撃リスク

**詳細**:
実装でトークン長の事前検証を行っています：

```typescript
// トークン長の検証（タイミング攻撃リスク）
if (requestToken.length !== sessionToken.length) {
  return { valid: false, error: ERROR_MESSAGES.CSRF_TOKEN_INVALID }
}

// timingSafeEqual（正しい比較）
```

このコードは、攻撃者にトークン長の情報を漏洩させる可能性があります。攻撃者が様々な長さのリクエストを送信し、応答時間の差異を分析することで、有効なトークンの長さを推測できます。

**修正方法**:

トークン長の検証を削除するか、**定数時間で長さを比較**するように変更します：

```typescript
// 定数時間での長さ比較
function constantTimeEqual(a: string, b: string): boolean {
  if (a.length !== b.length) {
    return false
  }
  return crypto.timingSafeEqual(
    Buffer.from(a.padEnd(CSRF_CONFIG.TOKEN_LENGTH * 2, '\0')),
    Buffer.from(b.padEnd(CSRF_CONFIG.TOKEN_LENGTH * 2, '\0'))
  ) || a.length === b.length  // 常にfalseを返すパスを追加
}
```

または、よりシンプルな解決策として、トークン長検証を完全に削除し、`timingSafeEqual`にのみ依存します：

```typescript
// シンプルにtimingSafeEqualのみを使用
// トークン長不一致の場合、timingSafeEqualは常にfalseを返す
// （バッファ長が一致しない場合はエラーではなくfalseを返す）
```

### 🟡 M-1: CSRFトークンのローテーション機能がない

**詳細**:
現在の実装では、CSRFトークンはセッションの有効期間（7日間）を通じて同じものが使用されます。長期間同じトークンを使用すると、トークンが漏洩するリスクが高まります。

**修正方法**:

以下のいずれかを実装します：

1. **時間ベースのローテーション**: 一定時間（例：1時間）ごとに新しいトークンを生成
2. **使用回数ベースのローテーション**: 一定回数（例：100回）の使用後に新しいトークンを生成
3. **二重トークン方式**: セッションID（長期）とCSRFトークン（短期）の組み合わせ

推奨は時間ベースローテーションです：

```typescript
// src/lib/csrf.ts
const CSRF_TOKEN_ROTATION_INTERVAL = 60 * 60 * 1000  // 1時間

export async function setCSRFToken(): Promise<string> {
  const session = parseSession(sessionCookie)
  
  // トークンのローテーション判定
  const shouldRotate = !session.csrfToken || 
    Date.now() - session.csrfTokenCreatedAt > CSRF_TOKEN_ROTATION_INTERVAL
  
  if (!shouldRotate && session.csrfToken) {
    return session.csrfToken
  }
  
  const token = generateCSRFToken()
  const updatedSession = {
    ...session,
    csrfToken: token,
    csrfTokenCreatedAt: Date.now(),
  }
  
  // ... 保存処理 ...
}
```

### 🟡 M-2: プリフライトリクエストの考慮不足

**詳細**:
`fetchWithCSRF`関数は、クロスサイトリクエストでプリフライト（OPTIONSリクエスト）を引き起こす可能性があります。特に、カスタムヘッダー（`X-CSRF-Token`）を使用する場合、ブラウザはOPTIONSリクエストを自動的に送信します。

現在の実装では、OPTIONSリクエストへの対応が考慮されていません。

**修正方法**:

```typescript
// src/lib/client/csrf.ts
export async function fetchWithCSRF(
  url: string,
  options: RequestInit = {}
): Promise<Response> {
  const method = (options.method || 'GET').toUpperCase()
  
  // OPTIONSリクエストはそのまま通過（プリフライト応答）
  if (method === 'OPTIONS') {
    return fetch(url, options)
  }
  
  if (['POST', 'PUT', 'DELETE'].includes(method)) {
    // ... 既存のCSRFトークン処理 ...
  }
  
  return fetch(url, options)
}
```

また、サーバー側にOPTIONSリクエストへの対応を追加：

```typescript
// src/lib/middleware/csrf.ts
export async function withCSRFProtection(
  handler: (request: NextRequest) => Promise<NextResponse>
): Promise<NextResponse> {
  return async (request: NextRequest) => {
    const method = request.method.toUpperCase()
    
    // OPTIONSリクエストは検証をスキップ
    if (method === 'OPTIONS') {
      return new NextResponse(null, {
        status: 204,
        headers: {
          'Access-Control-Allow-Origin': '*',
          'Access-Control-Allow-Methods': 'GET, POST, PUT, DELETE, OPTIONS',
          'Access-Control-Allow-Headers': 'Content-Type, X-CSRF-Token',
        },
      })
    }
    
    // POST/PUT/DELETEの検証
    if (['POST', 'PUT', 'DELETE'].includes(method)) {
      const validation = await validateCSRFToken(request)
      if (!validation.valid) {
        return NextResponse.json(
          { error: ERROR_MESSAGES.FORBIDDEN },
          { status: 403 }
        )
      }
    }
    
    return handler(request)
  }
}
```

### 🟡 M-3: グローバルミドルウェアでの強制検証がない

**詳細**:
現在の実装では、各APIルートで個別に`withCSRFProtection`を適用する必要があります。開発者が一部のルートで検証を忘れるリスクがあります。

**修正方法**:

Next.jsのmiddleware.tsでグローバルにCSRF検証を適用することを検討してください：

```typescript
// src/middleware.ts
import { NextResponse } from 'next/server'
import type { NextRequest } from 'next/server'
import { validateCSRFToken } from '@/lib/csrf'

const CSRF_PROTECTED_METHODS = ['POST', 'PUT', 'DELETE']
const CSRF_PROTECTED_PATHS = [
  '/api/upload',
  '/api/cards',
  '/api/gacha',
  '/api/battle',
  '/api/streamer',
  '/api/user-cards',
]

export async function middleware(request: NextRequest) {
  const { method, nextUrl } = request
  
  // 保護対象パスとメソッドか判定
  const isProtectedPath = CSRF_PROTECTED_PATHS.some(
    path => nextUrl.pathname.startsWith(path)
  )
  
  if (CSRF_PROTECTED_METHODS.includes(method) && isProtectedPath) {
    // CSRF検証（OPTIONSリクエストは除外）
    if (method !== 'OPTIONS') {
      const validation = await validateCSRFToken(request)
      
      if (!validation.valid) {
        return NextResponse.json(
          { error: 'Forbidden' },
          { status: 403 }
        )
      }
    }
  }
  
  return NextResponse.next()
}

export const config = {
  matcher: [
    '/api/:path*',
  ],
}
```

設計書と実装は基本的なCSRF保護として適切に構成されていますが、重大なセキュリティ問題が3つ検出されました：

1. **localStorage使用によるXSSリスク**（H-2）- 最も重要、早急に対応
2. **SameSite='lax'の誤解**（H-1）- 設計書の表現を更正
3. **トークン長検証のタイミング攻撃リスク**（H-3）- 検証方法を改善

実装の品質は良好であり、テストカバー率も高い水準に達しています。上記の指摘事項に対応することで、より堅牢なCSRF保護が実現できます。
