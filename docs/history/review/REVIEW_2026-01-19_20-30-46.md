## 2. Potential Bugs & Edge Cases

### Issues

#### B1: **Race Condition Fix Not Applied in Code Example (ARCHITECTURE.md)**
- **Location:** `docs/ARCHITECTURE.md` lines 245-252
- **Issue:** The code example in `setCSRFToken()` function still shows the vulnerable pattern:
  ```typescript
  if (session.csrfTokenHash) {
    const existingToken = getCSRFTokenFromCookie(cookieStore)
    if (existingToken) {
      return existingToken
    }
  }
  ```
- **This creates TOCTOU vulnerability** between checking `session.csrfTokenHash` and reading the cookie.
- **However**, `docs/IMPLEMENTED.md` (lines 56-61) shows the correct fix was applied:
  ```typescript
  const existingToken = getCSRFTokenFromCookie(cookieStore)
  if (session.csrfTokenHash && existingToken) {
    return existingToken
  }
  ```
- **Impact:** Developers implementing based on `ARCHITECTURE.md` will introduce the vulnerability.
- **Recommendation:** Update the code example in `ARCHITECTURE.md` to match the fixed implementation.

#### B2: **Missing Session Validation in `clearCSRFToken`**
- **Location:** `docs/ARCHITECTURE.md` lines 369-393
- **Issue:** `clearCSRFToken` function only deletes the CSRF token cookie but does not clear `csrfTokenHash` from the session cookie.
- **Code shows:**
  ```typescript
  const updatedSession = { ...session }
  delete updatedSession.csrfTokenHash  // This creates undefined property
  ```
- **Additionally**, `docs/IMPLEMENTED.md` (lines 78-80) shows the correct fix using destructuring, but `ARCHITECTURE.md` was not updated.
- **Impact:** Session may contain stale `csrfTokenHash` after logout, causing validation failures.
- **Recommendation:** Update `ARCHITECTURE.md` to show the destructuring pattern and ensure `csrfTokenHash` is properly cleared from session.

## 4. Security Considerations

### Positive Aspects

- **SameSite='lax' Configuration**: Properly configured to allow OAuth callbacks while blocking cross-site POST requests.
- **HttpOnly Session Cookie**: Prevents XSS attacks from accessing session data.
- **Comprehensive Attack Scenarios**: Architecture document covers various attack vectors.

### Issues

#### S1: **Inconsistent Security Pattern Documentation**
- **Issue:** `docs/ARCHITECTURE.md` heavily promotes "HttpOnly Cookie Pattern" (lines 144-179, 470-488) but the implementation uses Double Submit Cookie Pattern.
- **Security Impact:** The HttpOnly Cookie Pattern is actually more secure against XSS because the token cannot be accessed via JavaScript. The Double Submit pattern with `X-CSRF-Token` header is vulnerable if XSS exists.
- **Recommendation:** Consider migrating back to HttpOnly Cookie Pattern for stronger security, or clearly document why Double Submit was chosen over the more secure pattern.

#### S2: **Origin Header Validation Not Implemented**
- **Location:** `docs/ARCHITECTURE.md` line 42
- **Issue:** The architecture mentions "Request origin validation" but the implementation only checks the CSRF token.
- **Risk:** CSRF token validation alone may not be sufficient for all attack scenarios.
- **Recommendation:** Consider adding `Origin` or `Referer` header validation as an additional defense layer.
