# レビュー結果: CSRF保護の実装 (2026-01-19)

## 概要

docs/ARCHITECTURE.md で設計されたCSRF保護と、実際の実装コードをレビューしました。

## 結論

**重大な問題が発見されました。設計と実装の間に根本的な矛盾があります。**

---

## 問題1: 設計と実装のアーキテクチャ不一致

### ARCHITECTURE.md の設計

**アーキテクチャ**: Double Submit Cookie Pattern with Hash Comparison + Token Signing

設計内容（ARCHITECTURE.md:156-178）:
- セッションにはCSRFトークンのハッシュを保存（httpOnly）
- **別の非httpOnly cookieにCSRFトークンを保存（JavaScriptからアクセス可能）**
- **クライアントはcookieからトークンを読み取り、X-CSRF-Tokenヘッダーに設定**
- **サーバーはヘッダーの値のハッシュとセッションのハッシュを比較**

### 実際の実装

**アーキテクチャ**: HttpOnly Cookie Pattern

実装内容（src/lib/csrf.ts:108-109）:
```typescript
cookieStore.set(COOKIE_NAMES.CSRF_TOKEN, token, {
  httpOnly: true,  // ← 設計ではfalseになるべき
  ...
})
```

実装内容（src/lib/csrf.ts:156）:
```typescript
const requestToken = getCSRFTokenFromCookie(cookieStore)
// X-CSRF-Tokenヘッダーを使用していない！
```

### 問題点

| 項目 | ARCHITECTURE.md | 実装 |
|------|----------------|------|
| Cookie属性 | 非httpOnly | httpOnly |
| トークン送信方法 | X-CSRF-Tokenヘッダー | Cookie自動送信 |
| パターン名 | Double Submit Cookie | HttpOnly Cookie |

## 問題2: 署名機能（Token Signing）が未実装

### ARCHITECTURE.md の設計

「署名付きトークンの追加実装」セクション（ARCHITECTURE.md:1041-1247）で詳細に設計されています：

```typescript
function signToken(token: string): string {
  const hmac = createHmac('sha256', SIGNING_KEY)
  hmac.update(token)
  return hmac.digest('hex')
}

function verifyTokenSignature(token: string, signature: string): boolean {
  const expectedSignature = signToken(token)
  try {
    return timingSafeEqual(
      Buffer.from(expectedSignature),
      Buffer.from(signature)
    )
  } catch {
    return false
  }
}
```

### 実際の実装

`src/lib/csrf.ts` に署名関連のコードが存在しません。

## 問題3: fetchWithCSRFの実装が無意味

### 設計の意図（ARCHITECTURE.md:507-531）

```typescript
export async function fetchWithCSRF(
  url: string,
  options: RequestInit = {}
): Promise<Response> {
  const method = (options.method || 'GET').toUpperCase()
  
  if (['POST', 'PUT', 'DELETE'].includes(method)) {
    const csrfToken = getCSRFTokenFromCookie()
    
    if (!csrfToken) {
      throw new Error('CSRF token not found in cookie')
    }
    
    options.headers = {
      ...options.headers,
      'X-CSRF-Token': csrfToken,
    }
  }
  
  return fetch(url, options)
}
```

### 実際の実装（src/lib/client/csrf.ts:7-12）

```typescript
export async function fetchWithCSRF(
  url: string,
  options: RequestInit = {}
): Promise<Response> {
  return fetch(url, options)  // 何もしない！
}
```

### 問題点

実装されたHttpOnly Cookie PatternではfetchWithCSRFは意味をなさない（何もしない関数になる）。

## 問題4: APIエンドポイントの実装不一致

### ARCHITECTURE.md の設計（ARCHITECTURE.md:397-427）

設計では、クライアントにCSRFトークンを返す必要があります（非httpOnly cookieなのでJavaScriptから読み取る）。

### 実際の実装

HttpOnly Cookie Patternでは、トークンをクライアントに返す必要はありません（httpOnly cookieなのでJavaScriptからアクセスできない）。

しかし、`/api/csrf-token`エンドポイントが存在し、トークンを返しています（src/app/api/csrf-token/route.ts:20-22）。

### 問題点

HttpOnly Cookie PatternではこのAPIは無意味です。

## 修正案

### オプション1: HttpOnly Cookie Patternとして完結させる（推奨）

設計書を修正し、HttpOnly Cookie Patternを採用することを明記する。

修正内容：
1. ARCHITECTURE.mdを修正してHttpOnly Cookie Patternを説明
2. `/api/csrf-token`エンドポイントを削除（トークンを返す必要がない）
3. `fetchWithCSRF`を削除（何もしないので）

メリット：
- HttpOnly Cookie PatternはXSS攻撃に対してより安全
- 実装がシンプルでエラーが発生しにくい
- 既に実装されているコードを修正するだけで済む

### オプション2: 設計通りDouble Submit Cookie Patternを実装する

ARCHITECTURE.mdに従って実装を修正する。

修正内容：
1. CSRF_TOKEN cookieをhttpOnly: falseに変更
2. `validateCSRFToken`でX-CSRF-Tokenヘッダーを使用する
3. `fetchWithCSRF`でX-CSRF-Tokenヘッダーを設定する実装に戻す
4. Token Signingを実装する

メリット：
- 設計書との整合性が取れる
- Token Signingによりトークン改ざんを防止

デメリット：
- XSS脆弱性がある場合、CSRFトークンが窃取される可能性がある
- 実装が複雑

## セキュリティの観点

### HttpOnly Cookie Patternの評価

**メリット**:
1. XSS攻撃時にCSRFトークンが窃取されない
2. SameSite='lax'との組み合わせで強固なCSRF保護
3. 実装がシンプルでエラーが発生しにくい

**デメリット**:
1. クライアント側でトークンを操作できない（HttpOnly Cookie Patternとしては正常）

### 設計（Double Submit Cookie Pattern）の評価

**メリット**:
1. SameSite='strict'以外の状況でも動作可能
2. クライアント側でトークンを操作できる（デバッグ等）

**デメリット**:
1. XSS脆弱性がある場合、CSRFトークンが窃取される可能性
2. 実装が複雑（ヘッダー、cookie、ハッシュ比較）
3. Token Signingがないとトークン改ざんのリスク
