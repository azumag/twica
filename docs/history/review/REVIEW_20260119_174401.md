# CSRF Protection Code Review

**Date:** 2026-01-19
**Reviewer:** Code Review
**Scope:** CSRF Protection Implementation

---

## Executive Summary

This review identified a **critical design inconsistency** between the architecture specification and the implementation. The architecture specifies the **HttpOnly Cookie Pattern** (token in httpOnly cookie, auto-sent by browser, no client-side JS access), but the implementation contains **client-side code that attempts to access the httpOnly cookie**, which is impossible in browsers.

**Overall Assessment:** ⚠️ Requires Immediate Attention

---

## Architecture vs Implementation Comparison

| Aspect | Architecture (ARCHITECTURE.md) | Implementation |
|--------|-------------------------------|----------------|
| Cookie Type | httpOnly: true | httpOnly: true ✓ |
| Token Location | Cookie (auto-sent by browser) | Cookie ✓ |
| Client-side JS Access | NOT needed (HttpOnly) | Attempted (BROKEN) |
| Token Validation | Read from cookie | Reads from cookie ✓ |
| Header-based | NOT used | NOT used ✓ |

## Issues Found

### Critical (Severity: Critical)

#### 1. Client-side Code Attempts to Access httpOnly Cookie

**Location:** `src/lib/client/csrf.ts:1-36`

**Description:** 
The client-side code attempts to read the CSRF token from `document.cookie`, but since the cookie is httpOnly, it is NOT accessible via JavaScript. This code will always return `null` for the token.

```typescript
// src/lib/client/csrf.ts:1-14
function getCSRFTokenFromCookie(): string | null {
  const cookies = document.cookie.split(';');
  const csrfCookie = cookies.find(cookie => {
    const [name] = cookie.trim().split('=');
    return name === 'csrf_token';  // Looking for 'csrf_token' but cookie is httpOnly!
  });
  // ...
}
```

**Impact:**
- `fetchWithCSRF()` will throw "CSRF token not found in cookies" error
- All state-changing operations from the client will fail
- This effectively breaks the entire CSRF protection mechanism from a usability standpoint

**Root Cause:**
The architecture specifies HttpOnly Cookie Pattern, which does NOT require client-side token handling. The client-side code appears to be from a Double Submit Cookie Pattern implementation that was never fully replaced.

**Recommended Fix:**
Remove `src/lib/client/csrf.ts` entirely. The HttpOnly Cookie Pattern does NOT require client-side JavaScript to handle tokens - the browser automatically includes httpOnly cookies with requests.

### High (Severity: High)

#### 2. Test Expectations Conflict with Implementation

**Location:** `tests/unit/csrf.test.ts:87-122`

**Description:**
The unit tests expect the CSRF token cookie to have `httpOnly: false`, but the actual implementation sets `httpOnly: true`.

```typescript
// Test expects httpOnly: false (line 00119)
expect.objectContaining({
  httpOnly: false,  // CONFLICTS with actual implementation
  sameSite: 'lax',
})
```

But actual implementation:
```typescript
// src/lib/csrf.ts:111-118
cookieStore.set(COOKIE_NAMES.CSRF_TOKEN, token, {
  httpOnly: true,  // This is correct per architecture
  // ...
})
```

**Impact:**
- Tests pass with wrong expectations
- Tests do not verify the correct security property (httpOnly)
- Future refactoring may break tests or implementation

**Recommended Fix:**
Update the test to expect `httpOnly: true`, which matches both the architecture and implementation.

### Medium (Severity: Medium)

#### 4. Integration Tests Validate Header-Based Pattern

**Location:** `tests/integration/csrf.test.ts:14-50`

**Description:**
Integration tests validate that tokens are read from the `X-CSRF-Token` header, which contradicts the architecture's HttpOnly Cookie Pattern.

```typescript
// tests/integration/csrf.test.ts:14-50
it('should validate request with valid CSRF token in X-CSRF-Token header', async () => {
  const request = new NextRequest('http://localhost:3000/api/test', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      'X-CSRF-Token': 'valid-token',  // Header-based validation
    }
  })
  const result = await validateCSRFToken(request)
  expect(result.valid).toBe(true)
})
```

**Impact:**
- Tests validate incorrect behavior
- May mask actual issues with token validation

**Recommended Fix:**
Update integration tests to validate cookie-based token transmission (since httpOnly cookies are automatically sent by browsers).

## Conclusion

The **server-side implementation is correct** and follows the HttpOnly Cookie Pattern as specified in the architecture. However, the **client-side code is fundamentally broken** because it attempts to access an httpOnly cookie, which is impossible in browsers.

The HttpOnly Cookie Pattern is a valid and secure approach for CSRF protection. The key insight is that **no client-side JavaScript is needed** - the browser automatically includes httpOnly cookies with requests, and the server validates by reading the cookie value.

**The fix is simple:** Remove the client-side CSRF handling code (`src/lib/client/csrf.ts`) entirely, as it is not needed for the HttpOnly Cookie Pattern. The browser and server handle everything automatically.
