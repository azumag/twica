# 実装記録: CSRF Protection

## 実施日: 2026-01-19

## レビュー結果に基づく修正

### docs/REVIEW.md の主要な問題点

#### 優先度1: 即時対応

**Q1: アーキテクチャと実装の不一致**
- **問題**: ARCHITECTURE.mdではHttpOnly Cookie Patternを説明しているが、実装はDouble Submit Cookie Pattern
- **修正**: HttpOnly Cookie Patternへ完全に移行済み
  - CSRFトークンをhttpOnly cookieに保存（JavaScriptからアクセス不可）
  - ブラウザが自動的にトークンを送信する
  - X-CSRF-Tokenヘッダーは不要
  - fetchWithCSRFは削除済み

**B1: 競合状態の修正**
- **問題**: setCSRFToken()にTOCTOU脆弱性がある
- **修正**: 適用済み
  ```typescript
  const existingToken = getCSRFTokenFromCookie(cookieStore)
  if (session.csrfTokenHash && existingToken) {
    return existingToken
  }
  ```

**B2: clearCSRFTokenの修正**
- **問題**: セッションからcsrfTokenHashが適切に削除されていない
- **修正**: デストラクチャリングパターンを使用して適切に削除済み
  ```typescript
  const { csrfTokenHash: _csrfTokenHash, ...sessionWithoutCsrf } = session
  const updatedSession = {
    ...sessionWithoutCsrf,
    version: session.version + 1,
  }
  ```

#### 優先度2: 短期対応

**Q2: ドキュメントの冗長性**
- 修正履歴をdocs/history/architecture/ARCHITECTURE-2026-01-19.mdに移動済み
- ARCHITECTURE.mdには現在の実装（HttpOnly Cookie Pattern）のみを記述済み

## アーキテクチャ決定

### HttpOnly Cookie Pattern

選定理由:
1. XSS攻撃時にCSRFトークンが窃取されないため、より安全
2. 実装がシンプルでエラーが発生しにくい
3. SameSite='lax'との組み合わせで強固なCSRF保護が実現できる
4. クライアント側での追加実装が不要
5. OAuthフローとの完全な互換性

### 競合状態対策（楽観的ロック）
- セッションにバージョン番号を追加
- トークン生成時にバージョンを検証
- バージョンが不一致の場合、リトライ（最大3回、50ms間隔）
- 更新成功時にバージョンをインクリメント

## セキュリティ配慮

### ログ記録
- IPアドレスのSHA-256ハッシュ化（先頭8文字のみ）
- エンドポイントURLのサニタイズ（パスのみ）
- タイムスタンプのISO 8601形式記録
- ユーザーIDの記録（デバッグ用）

### エラーハンドリング
- クライアントへのエラーメッセージは汎用的に（ERROR_MESSAGES.CSRF_TOKEN_INVALID）
- ログメッセージは詳細に（検証失敗の理由、IP、ユーザーIDなど）
