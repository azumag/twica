# CSRF保護機能実装完了

## 実施日時

## レビュー結果に基づく実装

レビュー結果（docs/ARCHITECTURE.md および docs/REVIEW.md）に基づき、以下の設計変更を実装しました：

### 1. HttpOnly Cookieパターンの採用

- **変更**: CSRFトークンをhttpOnly cookieに保存（`httpOnly: true`）
- **変更**: X-CSRF-Tokenヘッダーの検証を削除
- **変更**: サーバー側でcookieからトークンを取得して検証

**理由**: XSS脆弱性がある場合、JavaScript経由でトークンを操作すること自体が問題であるため、トークンをJavaScriptからアクセス不可能にする。

### 2. SameSite属性の修正

- **変更**: CSRFトークンcookieのsameSiteを'lax'に変更（OAuthコールバックを許可）

**理由**: OAuthコールバックは外部ドメイン（Twitch）からのリダイレクトであるため、`sameSite: 'lax'`が必要。

### 3. 楽観的ロックの実装

- **変更**: セッションにversion番号を追加
- **変更**: setCSRFToken()関数で競合状態を回避

**理由**: 現在のidempotent設計では、セッションの読み取りと更新の間に別のリクエストが介入した場合、トークンが上書きされる可能性があるため。

### 4. エラーハンドリングの改善

- **変更**: エラーの種類に応じてログレベルを使い分け（INFO/WARN/ERROR）

**理由**: エラーの種類に応じて異なるログレベルを使用することで、より適切な監視が可能になる。

// 変更前
export async function fetchWithCSRF(
  url: string,
  options: RequestInit = {}
): Promise<Response> {
  const method = (options.method || 'GET').toUpperCase()

  // POST/PUT/DELETEの場合、CSRFトークンを追加
  if (['POST', 'PUT', 'DELETE'].includes(method)) {
    const csrfToken = getCSRFTokenFromCookie()

    if (!csrfToken) {
      throw new Error('CSRF token not found in cookie')
    }

    options.headers = {
      ...options.headers,
      'X-CSRF-Token': csrfToken,
    }
  }

  return fetch(url, options)
}

// 変更後
export async function fetchWithCSRF(
  url: string,
  options: RequestInit = {}
): Promise<Response> {
  // CSRFトークンはhttpOnly cookieに保存され、自動的に送信される

## セキュリティ根拠

### SameSite='lax'によるCSRF保護

SameSite='lax'は以下の動作をします：

1. **クロスサイトPOSTリクエストでCookieが送信されない**:
   - 外部サイトからのPOSTリクエスト（CSRF攻撃）でCookieが送信されない
   - これにより、CSRFトークンが含まれないリクエストは検証に失敗する

2. **トップレベルナビゲーションでCookieが許可**:
   - OAuthコールバックのようなトップレベルナビゲーション（GETリクエスト）でCookieが送信される
   - これにより、Twitchからのリダイレクトが正常に動作する

### ブラウザ互換性

SameSite='lax'は以下のブラウザでサポートされています：

- Chrome 51+ (2016年5月)
- Firefox 60+ (2018年5月)
- Safari 12+ (2018年9月)
- Edge 79+ (2020年1月)
- iOS Safari 12.2+ (2019年3月)
- Android Chrome 51+ (2016年5月)

### XSS脆弱性とCSRF保護の共存

HttpOnly Cookieパターンを採用した場合、XSS脆弱性が存在してもCSRF保護は有効です：

1. **XSS攻撃者がCSRFトークンを取得できない**:
   - `csrf_token` cookieはhttpOnlyであるため、JavaScriptから読み取れない
   - 攻撃者は`document.cookie`からトークンを取得できない

2. **SameSite='lax'による追加保護**:
   - クロスサイトPOSTリクエストでCookieが送信されない
   - 外部サイトからの攻撃はブロックされる

3. **ハッシュ比較による保護**:
   - セッションにはトークンのハッシュのみが保存される
   - 仮にトークンが漏洩しても、ハッシュ比較で検証される

## 実装のポイント

### HttpOnly Cookieパターン

- **メリット**: XSS脆弱性がある場合でも、CSRFトークンが窃取されない
- **メリット**: クライアント側の実装が簡素化される
- **デメリット**: X-CSRF-Tokenヘッダーによる追加の検証レイヤーがなくなる（SameSite='lax'で代用）

### SameSite='lax'

- **メリット**: OAuthコールバックが正常に動作する
- **メリット**: CSRF攻撃（POSTリクエスト）は防止される
- **デメリット**: `sameSite: 'strict'`よりは弱い（ただしCSRF保護としては十分）

### 楽観的ロック

- **メリット**: 競合状態を確実に回避できる
- **メリット**: 排他制御と比較してパフォーマンスへの影響が少ない
- **デメリット**: 再帰的なリトライが発生する可能性がある（ただし、現実的なシナリオでは稀）

### エラーハンドリング

- **メリット**: エラーの種類に応じて適切な監視が可能
- **メリット**: タイミング攻撃の疑いがある場合、早期に検知できる
- **デメリット**: ログの量が増える可能性がある（ただし、INFOレベルはフィルタリング可能）
