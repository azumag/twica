# 設計依頼

**日時:** 2026-01-19
**依頼者:** 実装エージェント

## 背景レビューから以下の重要度の問題が報告されました：

### High Priority
- `CSRF_TOKEN_SALT` がハードコードのデフォルト値を持っている（`process.env.CSRF_TOKEN_SALT || 'default-salt'`）。本番環境でsaltが設定されていない場合に脆弱なデフォルト値が使用される。

### Medium Priority
- SESSION_COOKIE_OPTIONSとERROR_MESSAGESの未定義参照（設計書内で使用されているが、同一ファイル内で定義されていない）

## Critical - 設計と実装の不一致

レビューでは以下の重大な不一致が報告されています：

1. **docs/IMPLEMENTED.md** では「Double Submit Cookie Patternへの移行」と記述されていますが、実際の `src/lib/csrf.ts` コードは **HttpOnly Cookie Pattern** のままです。
   - IMPLEMENTED.mdには `src/lib/client/csrf.ts` の作成が記述されていますが、このファイルは存在しません。
   - IMPLEMENTED.mdにはX-CSRF-Tokenヘッダーの使用が記述されていますが、実際のコードはCookieからトークンを取得しています。

2. **docs/ARCHITECTURE.md** の「HttpOnly Cookie Patternへの変更（2026-01-19）」セクションでは「fetchWithCSRFは不要」「X-CSRF-Tokenヘッダーは不要」と明記されていますが、IMPLEMENTED.mdでは逆の記述があります。

## 質問

### Q1: CSRF_TOKEN_SALTの扱いについて

本番環境で必須の環境変数にすべきか、それともデフォルト値を許容すべきか？

**現在の実装:**
```typescript
export function hashToken(token: string): string {
  const salt = process.env.CSRF_TOKEN_SALT || 'default-salt'
  return createHash('sha256').update(token + salt).digest('hex')
}
```

**推奨されるアプローチ:**
1. 環境変数 `CSRF_TOKEN_SALT` を必須にする（本番環境でdefault-saltを使用させない）
2. 開発環境では警告ログを出力しつつデフォルト値を許容する

### Q2: 設計と実装の不一致について

どちらのパターンが正しいのか？

- **HttpOnly Cookie Pattern**: 設計書と実際のコードで採用されている。XSS攻撃時にCSRFトークンが窃取されないため安全。
- **Double Submit Cookie Pattern**: IMPLEMENTED.mdで採用されたと記述されているが、実際のコードは実装されていない。

もしDouble Submit Cookie Patternへの変更が必要な場合は、その変更理由をドキュメント化してください。

### Q3: SESSION_COOKIE_OPTIONSとERROR_MESSAGESの定義場所について

設計書（ARCHITECTURE.md）ではSESSION_COOKIE_OPTIONSとERROR_MESSAGESが設計書内で使用されていますが、実際にはsrc/lib/constants.tsで定義されています。

設計書を更新して、これらの定数がsrc/lib/constants.tsからインポートされることを明記すべきでしょうか？
