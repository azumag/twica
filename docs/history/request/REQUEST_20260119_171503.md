## 最重大な問題

### 1. XSS脆弱性によりCSRF保護が完全に無効化される

**現在の実装:**
- セッションにはCSRFトークンのSHA-256ハッシュを保存（httpOnly）
- 非httpOnly cookieにCSRFトークンを保存（`httpOnly: false`, `sameSite: 'strict'`）
- クライアントはcookieからトークンを読み取り、`X-CSRF-Token`ヘッダーに設定
- サーバーはヘッダーのトークンをハッシュ化し、セッションのハッシュと比較

**問題点:**
- 非httpOnly cookieに保存された`csrf_token`は、XSS脆弱性がある場合に攻撃者が`document.cookie`から読み取れる
- 攻撃者は以下の手順でCSRF保護を回避できる:
  ```javascript
  const token = document.cookie.split('; ').find(row => row.startsWith('csrf_token=')).split('=')[1];
  fetch('/api/cards', {
    method: 'POST',
    headers: {
      'X-CSRF-Token': token,
      'Content-Type': 'application/json'
    },
    body: JSON.stringify({ /* 攻撃者のデータ */ })
  });
  ```
- ハッシュ比較はトークン値の漏洩を防ぐものではなく、トークン自体が漏洩すれば完全に無効

**質問1:**
Double Submit Cookie Pattern with Hash Comparisonの設計において、以下のいずれのアプローチを採用すべきでしょうか？

**アプローチA: HttpOnly Cookieパターン**
- CSRFトークンをhttpOnly cookieに保存
- SameSite='strict'または'lax'を使用
- クライアント側からはトークンに直接アクセスできない
- X-CSRF-Tokenヘッダーは不要（cookieが自動的に送信される）
- **課題:** OAuthコールバックが外部ドメインからのリダイレクトであるため、SameSite='strict'ではcookieが送信されない可能性がある

**アプローチB: Custom Request Headerパターン**
- トークンをlocalStorageに保存
- JavaScriptからカスタムヘッダー（X-CSRF-Token）に設定
- トークンをサーバー側のストレージ（セッション）に保存し、比較
- **課題:** XSS脆弱性がある場合、localStorageも攻撃者がアクセスできるため、cookieと同様にトークンが漏洩する

**アプローチC: Synchronizer Token Pattern（サーバー側ストレージ）**
- CSRFトークンをサーバー側（Redisなど）に保存
- クライアントにはトークンの署名付きバージョンのみを提供
- **課題:** 追加のインフラ（Redisなど）が必要
- **課題:** SPAとの相性が悪い可能性がある

### 2. SameSite='strict'によるOAuthコールバック失敗のリスク

**現在の実装:**
- `csrf_token` cookieを`sameSite: 'strict'`に設定
- セッションcookieを`sameSite: 'lax'`に設定

**問題点:**
- OAuthコールバックは外部ドメイン（Twitch）からのリダイレクト
- `sameSite: 'strict'`ではクロスサイトナビゲーションでcookieが送信されない
- 認証後にCSRFトークンが正常に動作しない可能性がある

**質問2:**
SameSite属性の適切な設定は以下のどれでしょうか？

**オプション1:**
- セッションcookie: `sameSite: 'lax'`（現在通り）
- CSRFトークンcookie: `sameSite: 'lax'`に変更
- 理由: OAuthコールバックを許可しつつ、CSRF攻撃を防止

**オプション2:**
- セッションcookie: `sameSite: 'lax'`（現在通り）
- CSRFトークンcookie: `sameSite: 'strict'`のまま
- 理由: より強力なCSRF保護（ただしOAuthコールバックでの問題を解決する必要がある）

**オプション3:**
- セッションcookie: `sameSite: 'lax'`（現在通り）
- CSRFトークンはcookieに保存せず、API経由で取得
- 理由: SameSiteの制約を受けない

### 3. トークン生成の競合状態

**現在の実装:**
- `setCSRFToken()`関数はidempotentであると記述されている
- 既にトークンが存在する場合は返す

**問題点:**
- セッションの読み取りと更新の間に別のリクエストが介入した場合、トークンが上書きされる可能性がある
- 同時実行リクエストが多いWebアプリケーションでは現実的な問題

**質問3:**
競合状態を回避するためのアプローチは以下のどれでしょうか？

**オプション1:**
- 現在のidempotent設計を維持
- コメントやドキュメントで制約を明記

**オプション2:**
- 楽観的ロック（Optimistic Locking）を実装
- セッションにバージョン番号を追加し、更新時に検証

**オプション3:**
- 排他制御（Pessimistic Locking）を実装
- セッション更新時にロックを取得（ただしパフォーマンスへの影響が懸念される）

---

### 4. エラーハンドリングの改善

**現在の実装:**
- `timingSafeEqual()`のエラーハンドリングはtry-catchで単純に処理
- エラー時は`ERROR_MESSAGES.CSRF_TOKEN_INVALID`を返す

**問題点:**
- バッファ長不一致などのエラーを検証失敗として処理するが、エラーメッセージは汎用的
- ログメッセージは詳細（IP、User-Agent、Referer、ユーザーIDなど）

**質問4:**
エラーハンドリングの改善方針は以下のどれでしょうか？

**オプション1:**
- 現在の設計を維持
- クライアントへのエラーメッセージは汎用的、ログは詳細

**オプション2:**
- エラーの種類に応じて異なるログレベルを使用
- バッファ長不一致はINFO、タイミング攻撃の疑いはWARN、その他はERROR

**オプション3:**
- Sentryに異常なパターン（短時間に多数の失敗など）を検知するアラート機能を追加

## 依頼事項

1. **XSS脆弱性とCSRF保護の共存**: XSS脆弱性がある場合でもCSRF保護が有効である設計アプローチをご提案ください
2. **SameSite属性の適切な設定**: OAuthコールバックを正常に動作させつつ、CSRF攻撃を防止するSameSite設定をご提案ください
3. **競合状態の回避**: 同時実行リクエストによるトークン上書きを防ぐアプローチをご提案ください
4. **エラーハンドリングの改善**: セキュリティとデバッグ性のバランスを考慮したエラーハンドリング方針をご提案ください
